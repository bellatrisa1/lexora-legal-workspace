## О проекте

🌐 Live Demo: https://lexora-legal-workspace.vercel.app/

**Lexora** — портфолио-проект международной legal tech платформы для юридических фирм, внутренних юридических отделов, независимых юристов и их клиентов.

В центре приложения находится **Matter** — юридическое дело или поручение: сопровождение сделки, проверка договора, регистрация интеллектуальной собственности или другая юридическая работа. Оно объединяет клиента, юрисдикцию, ответственную команду, документы, задачи, сообщения и историю действий.

Проект демонстрирует развитие юридического workspace от frontend-прототипа до локального fullstack-приложения: от публичной главной страницы до рабочих сценариев с валидацией, асинхронными запросами, обработкой ошибок и адаптивной навигацией.

> **Текущий этап — локальное fullstack-приложение с демонстрационными личностями.** Реализованы пять языков, Express REST API, PostgreSQL и миграции. Можно запустить и автономный mock-режим. Аутентификации и production-изоляции пользователей пока нет; все исходные записи вымышлены.

## Запуск Express + PostgreSQL

Создайте **отдельную пустую базу** и пользователя PostgreSQL для Lexora. Не направляйте демозаполнение на чужую или production-базу.

```bash
cp .env.example .env
```

Укажите в `.env` собственный `DATABASE_URL`. Пример файла содержит только шаблонные реквизиты. `.env` исключён из Git.

```dotenv
NEXT_PUBLIC_API_MODE=rest
API_INTERNAL_URL=http://127.0.0.1:4000
DATABASE_URL=postgresql://lexora:change-me@127.0.0.1:5432/lexora
DEMO_API_ENABLED=true
APP_ORIGIN=http://localhost:3000
API_PORT=4000
```

```bash
npm run db:migrate
npm run db:seed
npm run api:dev
```

В другом терминале запустите `npm run dev`. Express слушает только `127.0.0.1`. Next.js проксирует `/api/v1/*` на `API_INTERNAL_URL`, поэтому браузеру не требуется отдельная настройка CORS. `APP_ORIGIN` должен совпадать с адресом, по которому вы открываете frontend.

`db:migrate` применяет новые SQL-файлы последовательно в транзакции, сохраняет SHA-256 и отказывается принимать изменённую уже применённую миграцию. `db:seed` — отдельная повторяемая команда: добавляет отсутствующие демозаписи и не перезаписывает существующие изменения. Сервер при запуске ничего не очищает и не заполняет автоматически.

Чтобы вернуться к автономному режиму, задайте `NEXT_PUBLIC_API_MODE=mock` и перезапустите frontend. При смене режима для production-preview нужна новая сборка: публичная переменная встраивается в клиентский код.

### REST API

| Метод и путь                        | Действие                                                |
| ----------------------------------- | ------------------------------------------------------- |
| `GET /health`                       | Проверка работы процесса API                            |
| `GET /api/v1/workspace`             | Данные рабочего пространства для выбранной демоличности |
| `POST /api/v1/matters`              | Создание дела                                           |
| `PATCH /api/v1/matters/:id/status`  | Изменение статуса дела                                  |
| `POST /api/v1/matters/:id/messages` | Отправка сообщения                                      |
| `PATCH /api/v1/tasks/:id/status`    | Изменение статуса задачи                                |

API использует общие Zod-схемы и возвращает ошибки вида `{ "error": { "code": "invalidInput" } }`. Текст ошибки формируется frontend на выбранном языке. Для демонстрации передаются `x-demo-organization` и `x-demo-user`; это **не токены доступа и не аутентификация**. Не публикуйте API с этим механизмом идентификации. Запуск требует `DEMO_API_ENABLED=true` и блокируется при `NODE_ENV=production`.

Изменения статусов блокируют строку дела на время транзакции. Запись изменения и соответствующего события атомарна. Связи между организациями, клиентами, пользователями и делами дополнительно проверяются внешними ключами PostgreSQL.

Поток работы с данными:

```text
Страницы и компоненты
        ↓
TanStack Query + API facade
        ↓
Контракт WorkspaceApi
        ↓
Выбор адаптера через NEXT_PUBLIC_API_MODE
        ├── mock → данные в памяти вкладки
        └── rest → HTTP → Express → PostgreSQL
```

Бизнес-модели отделены от отображения и транспорта. У сущностей есть контекст организации. Юрисдикция, страна, язык, часовой пояс и валюта рассматриваются независимо друг от друга.

HTTP-адаптер находится в `src/lib/api/http.ts`, серверная реализация контракта — в `server/repository.ts`. Компоненты используют прежний `WorkspaceApi`. В REST-режиме перезагрузка страницы не удаляет изменения, а история записывается сервером в той же транзакции, что и действие. Проверки видимости выполняются сервером, однако личность ещё выбирается через недоверенные демозаголовки: это не полноценная авторизация.

### Демонстрационные данные

Файл `src/lib/fixtures.ts` содержит согласованный набор: одну организацию, шесть клиентов, семь дел, а также связанные документы, задачи, сообщения и события.

Например, **Northstar Acquisition** связан с клиентом **Asteria Technologies Ltd.**, юрисдикцией **England & Wales** и юристом **Olivia Bennett**. Эти связи используются в разных разделах приложения.

Mock API проверяет ввод и связи между сущностями, ограничивает клиентскую выборку и создаёт события изменений. Однако все эти операции выполняются в браузере и **не обеспечивают production-безопасность**.

## Сценарии для демонстрации

### 1. От нового дела до обновления статуса

1. Откройте **New Matter**.
2. Заполните название, клиента, направление практики, юрисдикцию, будущую целевую дату и описание.
3. Создайте дело и отправьте сообщение во вкладке **Messages**.
4. Измените статус в роли **Lawyer**.
5. Откройте **Activity** и проверьте историю действий.

### 2. Сотрудничество клиента и юриста

1. В **Settings** или навигации выберите демороль **Client**.
2. Откройте **Northstar Acquisition**, изучите документы и переписку.
3. Отправьте сообщение от лица клиента.
4. Переключитесь на **Lawyer** и ответьте вручную.
5. Обновите задачу и проверьте сроки в **Calendar**.

Автоматические ответы от имени юриста не генерируются. В **Help** можно дополнительно проверить ошибку API, повторную загрузку и сброс демонстрационных данных.

## Интернационализация и локализация

Интерфейс поддерживает **English, Русский, Español, Français и Italiano**. Переключатель доступен на главной, в верхней панели кабинета и в настройках. Переводятся навигация, формы, валидация, статусы, справочники юрисдикций и практик, уведомления, история, пустые состояния и справка. Имена, компании, сообщения, описания дел и названия файлов остаются пользовательским контентом и не переводятся.

### Как определяется язык

1. Сервер проверяет cookie `portal_locale`.
2. Если сохранённого поддерживаемого языка нет, разбирает `Accept-Language`, включая региональные варианты и веса предпочтений.
3. Если ни один язык не поддерживается, выбирает English.

Начальные переводы передаются в React Context с сервера; `<html lang>` соответствует языку. При переключении загружается нужный каталог, обновляется интерфейс и cookie на год. Перезагрузки страницы нет: черновики форм и кеш данных сохраняются. Язык не включён в URL, поэтому существующие ссылки продолжают работать. Это настройка workspace; отдельная SEO-структура публичного многоязычного сайта пока не реализована.

### Каталоги и добавление языка

Переводы лежат в `src/i18n/messages/{en,ru,es,fr,it}.json`. Ключи разделены по областям: `common`, `navigation`, `matters`, `documents`, `messages`, `validation`, `errors` и другим разделам. Тип `MessageKey` выводится из английского каталога. При отсутствии перевода отдельного ключа используется английский текст.

Чтобы добавить язык:

1. Добавьте код и название в `src/i18n/config.ts`.
2. Создайте JSON-каталог с теми же ключами и параметрами `{name}`, `{count}` и т. п.
3. Зарегистрируйте загрузчик в `src/i18n/messages.ts`.
4. Добавьте ожидаемое форматирование даты и браузерный сценарий в тесты.
5. Проверьте `npm test` и браузерные тесты: они сверяют ключи, параметры, переключение и сохранение языка.

Даты и числа форматируются через `src/i18n/format.ts` и `Intl`. Сроки без времени сохраняют календарную дату в UTC, временные метки используют выбранный независимо от языка часовой пояс. Валюта передаётся форматтеру явно. Настройка часового пояса действует в текущей вкладке; язык сохраняется в cookie.

| `npm run build`        | Production-сборка                |
| `npm run test:e2e`     | Браузерные проверки Playwright   |

**Vitest** проверяет валидацию, область видимости данных, создание и изменение записей, сообщения, события, восстановление после ошибок, локализационные утилиты и часовые пояса.

**Playwright** проверяет публичную главную, навигацию, поиск, фильтры, создание дела, статусы, сообщения, документы, демороли, диалоги и обработку ошибок на desktop и mobile в Chromium.

Перед первым запуском браузерных тестов установите браузер, если он ещё не установлен:

```bash
npx playwright install chromium
npm run build
npm run test:e2e
```

Тесты запускают production-сервер на `127.0.0.1:3107`. Этот порт должен быть свободен. Скриншоты и диагностические traces сохраняются в `test-results/`.

### Проверки реальной базы и REST

Задайте `TEST_DATABASE_URL` для **отдельной тестовой базы**. Интеграционные тесты создают уникальную схему, применяют миграции и seed, проверяют REST, транзакции и постоянство данных, затем удаляют только свою схему. Без этой переменной DB-тесты пропускаются при обычном `npm test`.

```bash
TEST_DATABASE_URL=postgresql://user:password@127.0.0.1:5432/lexora_test npm run test:integration
```

Для REST E2E сначала примените миграции и seed к тестовой базе, затем:

```bash
NEXT_PUBLIC_API_MODE=rest API_INTERNAL_URL=http://127.0.0.1:4001 npm run build
TEST_DATABASE_URL=postgresql://user:password@127.0.0.1:5432/lexora_test npm run test:e2e:rest
```

REST E2E запускает API на `4001`, frontend на `3108` и создаёт демонстрационные дела в указанной тестовой базе. Обычный набор использует порт `3107` и требует mock-сборку: `NEXT_PUBLIC_API_MODE=mock npm run build`. Конфигурации не переиспользуют уже запущенные серверы.

## Ограничения текущей версии

- REST-режим сохраняет данные в PostgreSQL; mock-режим по-прежнему сбрасывается после перезагрузки.
- Демороли не являются настоящим входом, безопасным RBAC или изоляцией арендаторов. API предназначен для локальной разработки.
- Файлового хранилища и загрузки на сервер нет. Скачиваемые образцы создаются браузером.
- История в REST-режиме сохраняется сервером, но до аутентификации нельзя считать её защищённым аудитом подтверждённых пользователей.
- Analytics отражает имеющиеся данные. Calendar — повестка сроков без внешней интеграции.
- Нет realtime, доставки уведомлений, фоновых задач, AI, платежей или production deployment.
- Исходные демосроки относятся к 2026 году, поэтому ближайшие дедлайны зависят от текущей даты.
- Приложение помечено `noindex` и не предоставляет юридических заключений.
